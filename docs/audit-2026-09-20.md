# pasm-framework 全面体检报告（2026-09-20）

> 对象：`pasm-framework` v0.1.0（独立成仓于 2026-09-20，从 `pasm_skills.framework` 拆出）
> 目的：全面检测框架是否完善、是否存在问题；并据此给出「插件化即插即用」改造方案。
> 结论先行：**框架当前是合格的「防腐层 / 骨架」，但还不是开箱即用的「应用开发平台」**——
> 它解决了"换引擎不重写智能体"的核心问题，但**缺少可扩展机制、传输层、LLM 接入、会话/租户、知识库摄取、护栏与可观测**，
> 导致"用它直接做出一个能上线的智能客服 / 站点助手"还需要补很多拼图。本次改造正是补齐这些拼图。

---

## 1. 当前架构盘点（v0.1.0 有什么）

pasm-framework 是一组**稳定表面（Stable Surface）**，职责是"产品应用 ↔ 认知引擎"之间的防腐层。

| 表面 | 类型 | 作用 | 评价 |
| --- | --- | --- | --- |
| `CognitiveBackend`（协议） | Protocol | 引擎侧契约（`episode_push/recall/feedback/learn_pick/counts`） | 单一真相源在基座 `pasm_skills.sdk.backend`，本仓只重导出 ✓ |
| `CognitiveService` / `CognitiveAssembler` | 类 | 引擎↔应用装配（**V1↔V2 唯一变动点**） | 设计正确，V2 只需加 `v2()` 工厂 ✓ |
| `DomainAdapter`（Protocol） | Protocol | 领域知识 / 规则注入 | 可选方法 + `getattr` 探测，设计稳 ✓ |
| `NullDomainAdapter` / `StaticDomainAdapter` | 类 | 空 / 静态领域实现 | 脚手架够用，真实领域需自行实现 |
| `Capability` / `CapabilityDiscovery` | 类 | 能力声明与统一发现（消灭散落 `if chip==`） | 句首 12 字匹配是产品侧有意设计 ✓ |
| `BaseApplication` | 类 | 通用 AI 应用底座（建在 `BaseAgent` 上） | 统一入口 `handle()` 已就位，但能力偏薄 |
| `BaseSkill` / `SkillManifest` | 类 | 技能包代码化底座 | 与 Capability 同源，方向对 |

**优点（必须保留）**
1. **依赖单向无环**：`pasm-agents → pasm-framework → pasm_skills.sdk → 引擎(pasm.*)`，无环。
2. **零依赖核心**：`BaseAgent` 不 import 任何 `pasm.*` 内部模块，离线可跑；档位（light/core/bionic）**降级永不隐藏**。
3. **V1↔V2 唯一变动点收敛**在 `CognitiveAssembler`，上层一行不改——这是框架存在的根本价值。
4. **表面契约清晰**：DomainAdapter / Capability / BaseSkill 三处都是"可被 surface-guard 自动验证"的稳定面。

## 2. 存在的问题 / 缺失（重点）

按"能否直接拿去开发一个**站点智能客服 / 通用 AI 应用**"的标准审视：

### P0 —  blockers（不补就上不了线）
- **[P0-1] 没有可扩展机制（插件 / Hook 链）**：所有 concern（会话、检索增强、回复生成、护栏）都写死在 `BaseApplication` 里，用户无法"在后端选择是否使用某项功能"。本次改造的核心就是补上**插件子系统**。
- **[P0-2] 没有传输 / 服务层**：`BaseApplication` 只有 `handle(text)→str`，没有 HTTP / WebSocket / iframe 出口。要让"站点通过外部链接接入智能客服"做不到。
- **[P0-3] 没有 LLM 接入点**：`chat()` 是纯模板渲染（离线优先没错），但真实产品需要 LLM。`BaseApplication` 没有"可选接入 OpenAI / DeepSeek / Ollama"的开关，用户只能自己去改 `_render_reply`。
- **[P0-4] 没有知识库 / 摄取能力**：只有情景记忆 `recall`（episode），没有"把站点数据 / FAQ 变成资料库并自学、记忆、成长"的机制——而这是智能客服的核心诉求。

### P1 — 重要缺失
- **[P1-1] 没有会话 / 租户模型**：`agent_id` 全局唯一、状态全局共享，多用户 / 多会话无法隔离（客服场景必需）。
- **[P1-2] 没有护栏（Safety）**：没有 prompt-injection 拦截、没有 PII 脱敏，直接对外暴露风险高。
- **[P1-3] 没有可观测（Observability）**：无指标、无健康检查、无延迟统计，线上排障靠猜。
- **[P1-4] 情绪没有"渲染"到回复**：`emotion_system` 内部有，但 `chat()` 模板基本不体现"有温度"，客服要的"有情感有温度"缺落点。

### P2 — 体验增强
- **[P2-1] 能力路由只支持句首关键词**：没有模糊 / 语义 / NLU 匹配（可接受，留待后续）。
- **[P2-2] `pyproject` 的 `packages` 只列了单包**：新增 `plugins` 子包后必须改成 `find` 或显式列出，否则打包会漏。
- **[P2-3] 没有"应用样例"**：仓库缺一个能跑的 `apps/` 参考实现（如客服），新用户上手成本高。

## 3. 优先级矩阵

| 缺失项 | 优先级 | 本次改造交付 |
| --- | --- | --- |
| 可扩展机制 | P0 | ✅ 插件子系统（`plugins/`）：契约 + Hook 链 + 注册表 + entry-point 发现 + `BackendConfig` |
| 传输/服务层 | P0 | ✅ `web_gateway` 插件（零依赖 `http.server`，支持 iframe / REST） |
| LLM 接入 | P0 | ✅ `llm_responder` 插件（OpenAI 兼容 / DeepSeek / Ollama，懒依赖、可关闭） |
| 知识库/自学 | P0 | ✅ `knowledge_base` 插件（站点数据摄取 + 自学习 QA 沉淀） |
| 会话/租户 | P1 | ✅ `sessions` 插件（会话隔离 + 历史） |
| 护栏 | P1 | ✅ `safety` 插件（注入拦截 + PII 脱敏） |
| 可观测 | P1 | ✅ `observability` 插件（指标 + 健康） |
| 温度渲染 | P1 | ✅ `warmth` 插件（情绪驱动的回复润色） |
| 样例 | P2 | ✅ `apps/customer_service.py` + `docs/customer-service-plugin.md` |

## 4. 插件化方案总览（本次实现）

**设计原则（不破坏现有防腐层）**
- 插件是**纯增量**：`BaseApplication` 仍只依赖稳定表面，`handle()` 在内部串起一条 **Hook 链**，插件挂在链上。
- **零依赖核心**：7 个 builtin 插件全部不强制外部包；`llm_responder` 用标准库 `urllib` 发请求，装了 `openai` 也能用，缺了照样不崩。
- **即插即用 / 后端可选**：通过 `BackendConfig`（一个 dict）控制每个插件的 `enabled` 与 `config`，**用户可在后端选择是否使用**。
- **可发现**：除 builtin 外，支持 `importlib.metadata` 的 entry-point（`pasm_framework.plugins` 组）自动发现第三方插件——生态可扩展。

**Hook 链（执行顺序）**
```
handle(text, session_id, user_id)
  └─ on_message_in   （safety 扫描 / sessions 绑定 / 语言）
  └─ on_retrieve     （knowledge_base 贡献事实 → 合并进 msg.facts）
  └─ 回复生成         （能力路由 cap.run → 否则 on_reply 插件生成 → 否则 chat 模板兜底）
  └─ on_reply        （llm_responder 生成 / warmth 润色，按注册顺序）
  └─ on_learn        （knowledge_base 自学习沉淀 / sessions 落地 / 反馈）
  └─ on_shutdown     （app.close() 时）
```

**`Message` 模型**（在链上流动的结构化消息）：`role / text / session_id / user_id / meta / facts / reply / stop / error / route_to`。插件只读可写这些字段，做到完全解耦。

## 5. 智能客服可行性（结论）

> 完整研究见 `docs/customer-service-plugin.md`。

**可行，且天然契合 PASM 的"记忆 / 情绪 / 成长"基因**：
- **自学**：`knowledge_base` 先摄取站点 FAQ / 文档形成资料库；每次高质量问答再沉淀为 QA 对 → 越用越懂（成长）。
- **记忆**：`recall`（情景 + 领域 + KB）让回复有依据、不瞎编；`sessions` 记住每个客户上下文。
- **有情感有温度**：`warmth` 插件把 `emotion_system` 的情绪与 persona 语气渲染进回复；`safety` 保证不被越权指令带偏。
- **高效部署**：`web_gateway` 提供 iframe 嵌入 + REST API，站点一行 `<iframe>` 即可接入；也支持 WebSocket（长连接）与脚本注入两种形态。

**已知局限（如实告知，路线图中处理）**：纯关键词 KB 检索精度有限（后续接向量检索）；LLM 依赖外部服务；多语言/方言需配置；合规（数据出境、PII 存储）需站点方配合。

- 扩展 `pasm_framework.selftest()`：覆盖插件装配、各 builtin 加载、KB 摄取+检索、safety 拦截、sessions 隔离、`handle` 端到端。
- 重跑三仓守门（framework / skills / surface-guard）全绿。
- 本地提交（**暂不推送**，结束询问后再推）。

> 本次改造**不启动 V2.0 引擎开发**（遵循"先完善再 V2.0"的既定约束）；所有改动只在应用层与插件层，引擎与 `CognitiveBackend` 协议零改动。
